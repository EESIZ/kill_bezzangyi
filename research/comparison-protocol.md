# Kill_bezzangyi ↔ unlazy 측정 설계

작성: 2026-09-23 · Task 5 · 상태: 설계 완료, 비교 실험 미실행.

## 1. 무엇을 확인할 것인가

핵심 질문은 **“중간의 반복적인 조정 판단을 스크립트로 옮기면, 실제 완수 수준을 유지하면서 전체 토큰과 시간이 줄어드는가?”**다.

검사기 실행 시간만 비교하지 않는다. 작업 해석, 분해, ACCESS 작성, 스킬 읽기, 명령 호출, 결과 해석, 재시도, 자식 에이전트, 병합, Gate 검증, Stop hook 이후 재개까지 비용에 포함한다. 계산을 밖으로 옮기는 데 들어간 비용도 우리 방식의 비용이다.

확인할 가설은 세 가지다.

- H1: 같은 작업 상태에서 다음 행동을 결정하는 토큰과 지연이 감소한다.
- H2: 그 절감이 초기 입력 작성과 상태 관리 비용을 상쇄해 실제 과제 전체에서도 남는다.
- H3: 누락·중복 실행·잘못된 완료·미병합 작업이 증가하지 않는다.

H1만 성립하면 “중간 판단 비용 감소”까지만 말한다. H2까지 측정해야 “전체 비용 감소”라고 말할 수 있다. 품질 차이가 불확실하면 “품질 유지 입증”이라고 쓰지 않는다. 아래 숫자와 판정 정책은 이 프로젝트의 제안이며 문헌이 보장한 임계값이 아니다.

## 2. 비교 대상을 고정한다

| 조건 | 고정할 대상 | 답하는 질문 |
|---|---|---|
| A: 출발 원본 | unlazy `16671491f6679ad9378f52604d3bc2415b4120c7`, source package 2.1.0 | 원본에 비해 우리 변경의 효과가 있는가? |
| B: 현재 파생본 | Task 2~4를 포함하는 Kill_bezzangyi 배포 파일 묶음 | 현재 구현 전체가 주는 이득과 비용은 무엇인가? |
| 선택 C: 사용자 설치본 | 설치된 unlazy 전체 패키지의 별도 고정 사본 | 사용자가 지금 쓰는 버전에서 교체할 가치가 있는가? |

A와 B가 주 비교다. C는 설치본의 내용이 출발 원본과 달라 별도 결과로 낸다. “최신 unlazy”처럼 움직이는 이름으로 비교하지 않는다. 최신판 비교를 추가한다면 조사 시점의 실제 커밋을 고정한다.

현재 저장소 HEAD는 `dfbf43276e1d42aa312ff1ee851a63b8087f692d`지만 Task 2~4 변경에는 미커밋 파일이 있다. **이 HEAD만으로 B를 식별할 수 없다.** 실행 전에 B를 커밋 또는 불변 아카이브로 고정하고, 포함 파일 목록·SHA-256·변경 diff를 함께 저장한다. 숨겨진 미추적 실행 파일도 빠뜨리지 않는다.

양쪽에 해당 스킬만 로드한다. 저장소 전체의 개발용 문서·벤치마크 정답·다른 스킬이 프롬프트로 섞이지 않게 동일한 배포 경계를 쓴다. 과제 저장소도 별도로 고정한다. 사용자에게 보여 주는 이름 차이는 기록하되 시험 중 스킬 내용을 편의상 고치지 않는다.

## 3. 측정은 세 층으로 나눈다

| 층 | 방법 | 결론의 범위 |
|---|---|---|
| ① 스크립트 정확성 | 동일 입력 반복, 오류 주입, 독립 검산, 기존 회귀 테스트 | 결정론·멱등성·복구의 구현 정확성 |
| ② 같은 상태에서 판단 | 똑같은 의존관계·접근 범위·실행 기록·완료 증거를 주고 다음 행동 결정 | 중간 조정 비용과 판단 오류 |
| ③ 실제 과제 전체 | 원래 사용자 요청부터 각 스킬이 해석·분해·구현·검증 | 사용자 관점의 전체 비용·시간·완수 |

①의 이전 검증 기록은 268/268 통과다. 이것은 토큰 절감 실험이 아니다. 동결한 후보 버전에서도 해당 회귀 검증을 다시 해야 한다.

②는 양쪽 모두 LLM이 스킬을 사용한다. B가 입력을 직렬화하고 스크립트를 호출하고 결과를 적용하는 비용도 포함한다. 순수 JavaScript 실행 시간은 별도 보조 수치다. “A의 LLM 전체”와 “B의 JavaScript만”을 비교하지 않는다. 동일한 초기 사실을 주는 층이므로 입력 사실을 처음 발견하는 비용은 ③에서 검증한다.

②의 정답은 독립된 검사기로 허용 가능한 다음 행동 집합을 판정한다. 여러 올바른 배정 순서가 가능하므로 특정 순서 하나만 정답으로 두지 않는다. 현재 선택기는 최대 병렬성이나 최적 스케줄을 보장하지 않는다. 의존성·충돌·동시 실행 한도·진행 가능한 작업의 불필요한 정지를 각각 검사한다.

③에서는 작업 분해를 강제로 같게 만들지 않는다. 분해·입력 생성의 차이와 실수도 실사용 효과에 포함한다. 대신 요청, 초기 파일, 도구, 모델, 자원 한도와 외부 합격 기준을 동일하게 둔다. 시험용 수집·채점 장치는 관찰용이며 제품에 새 실행 하네스를 도입한다는 뜻이 아니다.

## 4. 과제 구성

처음에는 아래 8개 유형을 동등하게 다룬다. 우리 방식에 유리한 병렬 과제만 고르지 않는다. 각 유형의 실제 프롬프트·fixture·독립 채점기를 만들고 동결하는 것은 다음 준비 단계다.

| 유형 | 유도할 상황 | 핵심 검사 |
|---|---|---|
| 1. 작은 단일 작업 | 한 함수 수정 등 분업 이득이 거의 없음 | 추가 준비 비용, 불필요한 분업 |
| 2. 긴 순차 작업 | 앞 결과가 있어야 다음 단계 수행 가능 | 의존성 위반, 쓸모없는 호출 |
| 3. 독립 분기 후 통합 | 독립 모듈들이 합쳐져 기능 완성 | 안전한 동시 진행, 통합 누락 |
| 4. 서로 다른 길이·교차 의존 | 일부 가지 완료 후 후속 작업만 시작 가능 | 모든 가지를 불필요하게 기다리는지 |
| 5. 통합 후 다시 분기 | 첫 통합 산출물에서 후속 독립 작업 발생 | 한 번의 분업으로 끝내 버리는지 |
| 6. 진행 중 추가 분할 발견 | 자식 작업에서 추가 독립 작업 확인 | 부모 보고, 다음 턴 재배정, 기존 결과 보존 |
| 7. 공유 파일·자원 충돌 | 겉으로 독립이나 쓰기·읽기 충돌 있음 | 잘못된 병렬 실행, 데이터 손상 |
| 8. 중단·중복 전달·재개 | 산출물 생성 뒤 반환 전달 중단 또는 중복 | orphan, 중복 부작용, 복구·최종 종료 |

②에는 유형당 대표 상태 1개를 주고 조건당 2회 반복한다: **8 × 2조건 × 2회 = 32개의 짧은 판단 실험**.

③의 예비 실험도 유형당 실제 과제 1개, 조건당 2회로 **32회**다. 두 층의 결과는 합치지 않는다. 예비 실험은 수집 가능성·오류·비용 규모를 파악하는 용도다. 총 64회가 이미 실행되었다는 뜻이 아니며, 32회로 일반적인 품질 동등성을 증명하지 않는다.

본 실험은 새로운 과제 인스턴스를 사용한다. 예를 들어 유형당 3개 과제 × 조건당 3회 × 2조건이면 144회지만, 이는 가능한 편성 예시일 뿐 필요한 표본 수의 증명이 아니다. 예비 실험의 과제 간 편차와 비용을 보고 표본 수를 결정한 뒤 고정한다. 같은 과제 반복만 늘리는 대신 서로 다른 과제를 확보한다.

주 실험은 네트워크 응답·시간·입력을 fixture로 고정한다. 예컨대 주식 사이트라면 상한가 판별용 종목 데이터와 장애 응답을 고정한다. 실제 시황의 변동이나 외부 사이트 제한을 스킬 차이로 오인하지 않는다. 실서비스 연결은 별도 현실성 시험으로 둔다.

## 5. 외부 기준으로 완료를 판정한다

각 과제의 필수 요구사항을 동결한 검사 집합 K로 만들고, 시험 대상이 수정할 수 없는 외부 채점기로 최종 산출물을 검사한다. 양쪽의 자체 Gate나 “완료했다”는 발언은 정답이 아니다.

실행 r의 품질과 종료를 구분한다.

```text
Q_r = ∏(k∈K) pass(r,k)             # 모든 필수 결과 검사가 통과하면 1
H_r = 1[abandon 없이 정상 인계하고 미수습 실행·누락·중복 부작용 없이 종료]
S_r = Q_r × H_r                   # 성공: 품질과 안전한 종료 모두 충족
F_r = 1[완료를 주장했지만 S_r=0]   # 잘못된 완료 선언
```

H는 공통 호스트 실행 기록과 실제 산출물로 평가한다. unlazy에 STRUCTURE 파일이 없다는 이유로 실패 처리하지 않는다. B 전용 registry 검산 실패는 별도의 내부 진단으로도 기록한다. “미병합”은 필수 결과가 최종 산출물에 통합되지 않은 경우이며 Git merge 명령 실행 여부가 아니다.

진행 중이지만 중단된 작업, 명시적인 abandon, Stop hook의 무진전 해제는 성공이 아니다. 실패·시간 초과·외부 도움 요청은 서로 구분하고 비용을 남긴다. 화면 품질처럼 주관적인 항목이 필요하면 기능 정답과 분리하고, 조건을 가린 독립 평가와 불일치 조정 규칙을 사전에 정한다.

## 6. 토큰과 시간의 계산 경계

부모와 모든 후손 에이전트의 고유 모델 요청 ID 집합을 J_r로 둔다. 재시도와 실패한 요청도 사용량이 발생했다면 포함한다.

```text
T_r = Σ(j∈J_r) (input_total_j + output_total_j)
W_r = t_final_quiescence − t_first_request
```

- input_total은 캐시된 입력을 포함한 전체 입력이다. cached_input이 그 부분집합이면 다시 더하지 않는다. 공급자가 입력·캐시 읽기·캐시 쓰기를 별도 항목으로 주면 공식 정의를 확인해 겹치지 않는 전체 입력으로 정규화한다.
- reasoning이 output_total의 부분집합이면 다시 더하지 않는다. 캐시·reasoning 상세는 별도 열로 보존한다. 호스트가 이미 집계한 자식 합계와 자식별 사용량을 중복 합산하지 않는다.
- 스킬·초기 컨텍스트 읽기부터 포함한다. 공급자 usage가 없으면 NA로 남긴다. 대화 길이 추정치나 계정의 남은 사용량 퍼센트를 실제 실행 토큰으로 대체하지 않는다.
- 종료는 부모의 마지막 발언만으로 정하지 않는다. 모든 해당 실행이 반환·정지되고 최종 인계가 끝난 시점이다. 버려진 자식이 남으면 시간 한도까지 실패로 추적하고 정리 비용도 기록한다.
- 실행 시간 한도에 도달하면 공통 호스트 정책으로 중단한다. 작업 구간과 정리 구간 시간을 각각 보존하고 총 W에도 포함한다. 정리 완료를 확인할 수 없으면 W는 우측 검열로 표시하고 완료 시간 평균에 끼워 넣지 않는다. 관찰 종료 시점까지의 시간·토큰과 사용량 누락 여부는 그대로 공개한다.
- 병렬 자식 실행 시간을 합한 값은 벽시계 시간과 다르다. 합계 실행 시간은 보조 지표로만 둔다.
- 독립 채점 비용은 실험 비용으로 따로 기록한다. 스킬이 수행하는 자체 검증·수정 비용은 T와 W에 포함한다. 외부 채점 결과를 에이전트에게 돌려주어 고치게 하지 않는다.
- 사람 개입 없는 시험을 기본으로 한다. 사람이 구조하거나 답을 알려 준 실행은 별도 상태로 남기고 무인 성공으로 세지 않는다. 대기 시간을 사후에 선택적으로 빼지 않는다.

현금 비용을 비교한다면 모델·날짜별 단가와 캐시 과금 항목을 고정해 서로 겹치지 않는 청구 항목에 곱한다. 구독 환경에서는 이 값을 실제 결제액으로 부르지 않고 “동일 단가 환산 비용”으로 표기한다. 캐시 효과 때문에 토큰 절감률과 비용 절감률은 다를 수 있다.

## 7. 어디서 비용이 생겼는지 보조 기록

전후 상태·도구 이벤트를 기준으로 해석/분해, 입력 작성, 배정, 실제 구현, 병합/인계, 검증/재개를 태그한다. 한 모델 요청에 여러 단계가 섞이면 mixed로 남긴다. 숨겨진 사고 과정을 요구하거나 임의로 전체 입력 토큰을 단계별로 나누지 않는다.

모델 호출 수, 스크립트 호출 수·실행 시간·출력 바이트, native spawn/return, 유휴 대기, 반복 보고, 실제 재실행, 잔여 작업, 사람 개입을 함께 기록한다. 원인 설명용 지표이며 전체 T와 W를 대체하지 않는다. 동일 상태가 몇 번 제공되었는지도 기록하되 그 상태에 사용된 추론 토큰을 정확히 분리했다는 주장은 하지 않는다.

실패 확률을 복잡도 입력으로 추정하는 접근과 다르다. 여기서 성공률은 실제 시험 결과의 집계일 뿐, 스케줄러가 사용하는 사전 확률이 아니다.

## 8. 반복·순서·환경 통제

같은 과제·반복 번호를 A/B 한 쌍으로 묶는다. 모델 버전, reasoning 설정, 도구·권한, native 동시 실행 한도, 초기 저장소, 의존성, 시험 예산을 같게 둔다. 양쪽이 사용한 실제 동시성은 결과로 기록한다.

각 과제의 첫 쌍은 사전에 저장한 난수 seed로 AB/BA를 결정하고 두 번째 쌍은 반대 순서로 실행한다. 각 실행은 새 세션·분리된 작업 폴더를 쓴다. 속도 비교 중 A/B를 같은 제한 자원에서 동시에 실행하지 않고 가까운 시간대에 번갈아 실행한다. 새 세션이 캐시 초기화를 보장하지는 않으므로 캐시 적중량과 실행 순서를 기록하고 캐시 조건별 결과도 본다.

이는 과제와 환경 변동을 묶어 비교하려는 설계다. 통제 가능한 요인을 블록으로 묶고 나머지 순서를 무작위화하는 원칙을 참고한다. [NIST: Randomized block designs](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)

예산은 유형별 동일 시간·동일 누적 토큰 한도로 설정하고 실행 전에 숫자를 고정한다. 현재는 실제 과제와 usage 수집 호스트가 미확정이므로 수치를 임의로 확정하지 않는다. 예비 실험 도중 한도를 바꾸면 새 실험 버전으로 구분한다. 결과가 유리해지는 시점에 반복을 중단하지 않는다.

누적 토큰 한도는 부모와 모든 후손을 합친 값이다. 실행 중 요청의 사용량이 나중에 도착해 한도를 넘길 수 있으므로 새 요청을 차단하는 규칙과 진행 중 요청의 취소 정책도 동일하게 적용하고, 실제 초과량을 기록한다. 토큰 수집 자체가 불가능하면 토큰 한도 준수나 정확한 토큰 비교가 가능하다고 표시하지 않는다.

모델 오류·스킬 오류·시험기 장애를 구분한다. 외부 수집기 장애 같은 사전 정의된 무효 사유만 제외 가능하다. 제외된 원본 행과 사유는 보존하며 A/B 쌍 전체를 별도 반복 ID로 다시 실행한다. 스킬이 실패했거나 토큰이 많이 들었다는 이유로 제외하지 않는다.

## 9. 중단·멱등성과 Stop hook 시험

공통 복구 시험은 “자식 산출물은 생성됐으나 부모가 반환을 받기 전”처럼 의미가 같은 사건에 맞춰 주입한다. 몇 초 뒤나 몇 번째 호출 뒤로만 정하면 양쪽의 서로 다른 단계가 중단될 수 있다. 해당 사건에 도달하지 못한 실행도 전체 과제 결과에서 제외하지 않고, 복구 시험 노출 여부를 따로 표시한다.

중복 반환 전달, 같은 보고의 재수신, 부모 재개 후 다음 배정, 완료 후 종료 시도를 관찰한다. 영속 상태의 멱등성과 native 호출·파일 변경 같은 외부 부작용의 중복은 별도 검사한다. 스크립트 상태가 멱등적이어도 외부 호출까지 exactly-once라는 뜻은 아니다.

B의 동일 operation/payload 적용에서 영속 논리 상태를 P라 하면:

```text
P(apply(e, apply(e, s))) = P(apply(e, s))
```

논리 턴, 작업 ID, Gate, receipt와 기록은 재시도로 중복 증가하면 안 된다. 다른 payload에 같은 ID를 쓰면 거절해야 한다. 이 B 전용 검사는 A에 없는 API를 억지로 요구하지 않고 ①에서 수행한다. 예외 주입 복구와 프로세스 강제 종료·남은 잠금의 복구는 구분한다. 사람이 잠금을 정리했다면 개입을 기록한다.

Stop hook은 두 조건에 같은 사용 여부·설정을 적용한다. 실제 호스트가 hook을 자동 실행하는지 먼저 검증한다. Claude Code용 hook 파일을 Codex에서 수동 호출한 결과는 “hook 모의 검사”이며 “실제 자동 재개 성능”이 아니다. hook 지원 호스트와 미지원 호스트 결과를 섞지 않는다. 종료 시도 횟수·block 횟수·재개 토큰·최종 잔여 실행을 기록하고, 6회 무진전 해제나 abandon으로 빠져나온 상태를 성공으로 처리하지 않는다.

## 10. 집계와 판정

과제 i, 조건 a의 반복 평균을 T̄_ia, W̄_ia, S̄_ia라 둔다. 유형마다 같은 수의 과제를 편성하고 과제별 동일 가중치 w_i=1/m를 사용한다. 불균형 편성이 필요하면 유형별 동일 가중치 후 유형 안에서 과제별 동일 가중치를 사전에 고정한다.

```text
P_a       = Σ_i w_i S̄_ia
ΔP        = P_B − P_A
R_T       = (Σ_i w_i T̄_iB) / (Σ_i w_i T̄_iA)
TokenSave = 1 − R_T
R_W       = (Σ_i w_i W̄_iB) / (Σ_i w_i W̄_iA)
TimeSave  = 1 − R_W
```

실패·시간 초과도 자원 집계에 포함한다. usage 누락이나 미정리 실행이 있으면 완전한 전체 지표를 산출할 수 없다고 표시하며, 관찰 가능한 하한과 누락 건수를 낸다. 일부 완전한 쌍만의 결과는 보조 분석이라고 표시한다. 실패가 빨리 끝나서 싸고 빨라진 결과를 개선으로 승인하지 않는다.

추가로 `ΣT / ΣS`를 “이 시험 묶음의 성공 1건당 지출”로 제시할 수 있다. 성공 0건이면 정의되지 않는다. 독립 재시도를 가정한 미래의 기대 비용으로 해석하지 않는다. 양쪽 모두 성공한 쌍에서의 절감률은 유용하지만 선택 편향이 있으므로 보조 결과다.

판정 순서는 다음과 같다.

1. 관측 품질: 필수 기능 실패, 잘못된 완료, orphan·중복 부작용을 먼저 비교한다. A 성공/B 실패 쌍은 전부 원인 검토하며 다른 과제의 절감으로 상쇄하지 않는다.
2. 전체 비용: 추가 입력·관리 비용까지 포함한 R_T를 본다.
3. 전체 시간: R_W를 따로 본다. 더 싸지만 느린 경우를 그대로 표시한다.
4. 범위: 과제 유형별 결과와 전체 결과를 함께 낸다. 병렬 과제에만 이득이면 그 조건에 한정해 결론을 쓴다.

예비 실험은 원시 성공 건수·짝별 차이·분포를 중심으로 보고한다. 본 실험에서는 과제를 묶음 단위로 재표집하는 paired cluster bootstrap 등으로 A/B 짝과 같은 과제의 반복을 보존해 95% 구간을 산출한다. 유형을 층으로 유지한다. 모델 요청 수를 독립 표본 수처럼 사용하지 않는다. 유형당 과제 하나뿐인 예비 실험에서는 새로운 과제로의 불확실성을 충분히 추정할 수 없다.

“통계적으로 차이가 검출되지 않았다”는 “품질이 같다”가 아니다. 본 실험에서 정식 비열등성을 주장하려면 허용 가능한 성공률 저하 δ와 표본 수를 실행 전에 따로 정해야 한다. 판정식은 `LowerCI(ΔP)>−δ`다. 임의의 δ를 숨겨 사용하지 않는다. δ 미합의 상태에서는 품질 동등성 주장을 보류하고 관측 결과만 제시한다. 토큰 우위의 통계적 근거는 `UpperCI(R_T)<1`, 시간 우위는 `UpperCI(R_W)<1`로 구분하며 품질 검토를 대체하지 않는다.

## 11. 저장할 자료와 실행 전 준비

실행별 요약 행에는 최소 다음 항목을 둔다.

| 묶음 | 필수 필드 |
|---|---|
| 식별 | experiment_version, run_id, pair_id, task_id, family, repetition, arm, execution_order |
| 고정 조건 | skill_manifest_hash, task_hash, grader_hash, model/version, reasoning, host/version, tool_config_hash, hook_mode, concurrency_cap, time/token_budget |
| 관측 | start/end, cleanup_duration, status, Q/H/S/F, requirement_results, intervention_count, fault_exposure, cache_usage |
| 비용 | unique_request_count, input_total, output_total, token_total, usage_complete, wall_time, timing_censored, script_duration, evaluator_cost |
| 근거 | transcript_path, request_usage_path, native_events_path, initial/final_artifact_hash, grader_log, exclusion_reason |

모델 요청별 원본 usage와 부모/자식 연결 ID, native 실행·반환·정지 기록, 스크립트 입출력, snapshot을 별도로 보관한다. 호스트가 제공하는 기록 범위만 수집하고 비공개 사고 과정의 노출을 요구하지 않는다. 최종 표는 저장된 자료만으로 재생성 가능해야 한다.

실행 전 준비 순서:

1. A/B 패키지 동결과 배포 파일 manifest 생성.
2. 사용할 호스트에서 부모·후손 요청별 usage와 실제 hook 동작의 수집 가능성 확인. 미지원이면 계측 가능한 호스트로 옮기거나 측정 가능한 범위만 명시.
3. 8개 과제 및 대표 상태, 고정 데이터, 외부 합격 검사, 의미 기반 중단 지점 작성. 채점기의 정답·오답 대조군 검증.
4. 시간·토큰·동시성 한도, AB/BA 순서, 누락·재시도 정책 고정.
5. 소규모 수집 점검 후 설계를 동결하고 예비 비교 실행. 점검 실행은 효과 분석에서 분리.

현재 완료된 것은 측정방법 설계다. 실제 과제 세트·계측 실행기·실험 예산 숫자·B의 동결본은 아직 준비 대상이며, 실제 토큰 절감률은 없다. 프로토콜 수정 후 같은 데이터를 확증용으로 재사용하지 않는다.
