# 검증 절차 최소화 설계 v1

상태: **재설계 및 작은 모델 검산 완료. 활성 스킬에 적용되지 않은 제안.**

## 1. 목표와 변경 범위

작업을 반환할 때마다 전체 설계와 이미 확인한 결과를 다시 읽는 흐름을 줄인다. 처음 정한 계약에 맞춰 작업하고, 공식 검증은 해당 산출물의 버전마다 한 주체가 수행한다. 전체 검토는 실제 통합 지점에 배치한다. 변경·실패·설계 판단이 필요한 사건만 별도로 검토한다.

“모든 검사를 마지막까지 미룬다”는 설계가 아니다. 뒤 작업이 앞 작업 결과를 사용하는 경우 앞 작업의 필요한 계약 검사는 먼저 통과해야 한다. 독립 작업 사이에는 전역 대기 장벽을 만들지 않는다.

unlazy의 완료 조건·독립 검사·통합 검사·고아 작업 방지 목적은 유지하지만, **자체 검사→부모의 동일 검사→조상에서 같은 자식 검사 재실행**이라는 절차를 그대로 보존하지 않는다. 이는 문구만 줄이는 변경이 아니라 검증 정책 변경이다. 기존 실행 코드와 스킬은 이 문서만으로 변경되지 않는다.

## 2. 목표 흐름

```text
설계·의무·연결 규격·검사 위치 확정
  ↓
스크립트가 실행 가능한 작업 계산
  ↓
작업자: 제작 + 필요한 개발 테스트 → 산출물 반환
  ↓
부모 측 검사기: 공식 검사 1회 + 현재 상태 기록
  ├─ 통과: 정확한 lease 해제 → 다음 작업 배정
  ├─ 검사 실패: 해당 작업에 구조화된 수정 요청
  └─ 계약 변경/해석 불가/근거 부족: 부모 의미 검토
  ↓
실제 합치는 지점에서만 통합 검사
  ↓
루트 통합 결과 검사 + 전체 요청 대조 + 잔여 상태 점검
```

“1회”는 같은 의무와 변경되지 않은 관측 입력에 대한 공식 성공 검사 1회다. 실패 후 수정, 입력 변경, 비결정적인 외부 상태, 새 검증 의무가 생기면 다시 실행한다. 최종 검증도 여러 검사를 묶은 단계일 수 있으며, 모든 시스템을 단일 테스트 한 번으로 보장한다는 뜻이 아니다.

## 3. 네 가지 검증 종류

| 종류 | 담당 | 실행 시점 | 반복 조건 |
|---|---|---|---|
| 계약 검토 | 부모 LLM/필요시 사람 | 최초 설계, 의미가 바뀐 계약 개정 | 요구사항·접근·인터페이스·검사 의미 변경 |
| 지역 공식 검사 | 부모 측 자동 검사기 | 해당 작업이 반환하고 필요한 입력이 고정됐을 때 | 실패/입력·검사·환경 변경/새 의무 |
| 통합 검사 | 부모 측 자동 검사기 + 명시된 수동 검토 | 실제 결과가 합쳐져 계약 경계를 넘을 때 | 통합 결과·관련 입력 변경 |
| 상태·보존 검사 | 스크립트 | 상태 변경·실행 직전·최종 종료 | 현재 상태가 바뀌면 가볍게 재확인 |

작업자의 테스트는 구현·디버깅 목적이다. 자체 통과 보고만으로 공식 완료 증거를 만들지 않는다. 모든 leaf에 전체 공식 Gate 실행이나 정해진 횟수의 전체 재독을 강제하지 않는다. 작업자가 디버깅에 같은 테스트를 실행했을 경우 부모 검사와 실제 중복이 생길 수 있으며, 그 실행도 비용에 포함한다.

수동 검토가 필요한 의무는 자동화했다고 표시하지 않는다. 다음 작업에 필요한 의미 판단이면 중간에 수행한다. 최종 결과에만 해당하는 검토는 최초 계약에서 통합/루트에 배치한다. 작업 시작 뒤 미통과 항목을 없애기 위해 검토를 임의로 이동하지 않는다.

## 4. 원본 절차에서 바꿀 부분

| 기존 규칙 | 제안 |
|---|---|
| leaf는 모든 Gate를 통과시킨 뒤 반환 | 필요한 개발 테스트와 산출물을 반환. 공식 수락은 부모 측 검사기 책임 |
| 부모는 반환된 leaf의 동일 Gate를 다시 실행 | 부모의 독립적인 첫 공식 실행은 유지. 자동 Gate만 있으면 별도의 전체 의미 재검토를 강제하지 않음 |
| 모든 반환에서 통과 Gate 하나를 반박하려고 시도 | 검사 자체의 부정 대조군·의미 검토는 최초/검사 변경 때 수행. 산출물 수동 검토는 계약에 명시된 범위에서 수행 |
| branch N1이 자식의 `--reverify`를 재귀 호출 | 각 자식에 대한 현재 공식 증거를 검산. 낡거나 부족한 증거만 재실행 요청 |
| branch마다 interface/E2E/regression 틀 복제 | 실제 통합 의무를 관찰하는 가장 적절한 한 지점에 배치. 상위는 그 증거와 새 통합 의무만 검사 |
| N5 lease 해제를 수동 증거로 확인 | 정확한 attempt/lease 기록으로 기계 확인. 실제 writer 종료 사실을 기록만으로 추정하지 않음 |
| 상위 단계에서 같은 수동 검토를 반복 | 같은 의무·같은 대상의 유효 검토는 재사용. 실제 독립적인 2차 검토가 필요한 의무는 별도 유지 |
| 종료 때 모든 자식 명령을 재귀 재실행 | 현재 증거·루트 통합 결과·전체 요구사항·잔여 작업을 확인. 누락/변경은 관련 작업으로 되돌림 |

원본의 `VERIFIED`는 독립 검사 완료라는 의미를 유지한다. 자식 자체 보고나 단순한 `--status`로 그 상태를 부여하지 않는다. 현재 코드의 `--status`는 산출물 신선도를 확인하지 않으므로 새 증거 검산기의 대용으로 쓰지 않는다.

현재 원본의 N1 CHECK를 그대로 두고 “실행하지 말라”는 지침만 추가하면 충돌한다. 새 정책에서는 템플릿·호출 경로·증거 규칙을 함께 바꿔야 한다. 기존 Gate를 자동 삭제하거나 원래 의무를 조용히 완화하는 마이그레이션은 하지 않는다.

## 5. 검사 위치를 정하는 규칙

각 요구사항/의무 ID는 하나의 공식 관찰 위치와 연결한다. 이름이나 명령이 같다는 이유로 서로 다른 의무를 병합하지 않는다. 한 검사로 여러 의무를 충족한다고 판단할 때는 최초 계약 검토에서 관찰 범위의 대응을 명시한다.

1. 해당 부품만으로 판단 가능하면 지역 검사다.
2. 두 결과를 실제로 연결해야 판단 가능하면 가장 낮은 해당 통합 지점의 검사다.
3. 단지 작업을 관리하기 위한 그룹에는 새 전체 검증을 만들지 않는다.
4. 합친 결과가 다시 다른 부품과 연결될 때 새 성질이 생기면 새 통합 검사는 필요하다.
5. 임의 개수의 가지가 끝났다는 이유나 논리 턴이 증가했다는 이유만으로 전체 검토를 추가하지 않는다.

예: 왼팔·몸통·오른팔의 치수 검사는 지역에서, 소매와 몸통의 연결은 조립 단계에서, 단추 수와 전체 착용 요구조건은 이를 직접 관찰할 수 있는 단계에서 검사한다. 단추 부착은 몸통을 필요로 할 수 있으므로 부자재 준비와 실제 부착을 혼동하지 않는다.

미래 작업이 미리 설계돼 있으면 작업자 수 제한으로 순서가 바뀌어도 재설계하지 않는다. 같은 에이전트 재사용은 호스트가 지원하고 문맥이 적합할 때만 한다. 숨은 분할을 발견하면 기존 report→정지 확인→정확한 반환→다음 턴 수락 절차를 유지하며 해당 계약 개정을 검토한다.

## 6. 공식 증거와 무효화

기존 Gate의 명령·EXPECT 지문만으로는 현재 산출물을 검증했다고 볼 수 없다. 새 정책을 구현하려면 아래 정보가 필요하다.

```text
Evidence(g) = {
  obligationId, contractRevision, verifierVersion,
  gateDefinition, runtimeIdentity,
  observedInputIdentity, closureMode,
  attemptIdentity, result, completionRecord
}

closureMode ∈ {complete, workspace, volatile}
```

- `complete`: 검사 결과를 좌우하는 전체 의존성을 알며 파일/도구/관련 환경을 식별할 수 있다. ACCESS의 작업 접근 선언을 검증 의존성 완전성의 자동 증명으로 사용하지 않는다.
- `workspace`: 개별 의존성을 모르면 검사 관련 전체 작업 공간과 도구 환경을 보수적으로 관찰한다. 관련 작업 공간이 바뀌면 기존 증거를 무효화한다. 관리 로그만 달라진 경우를 제외하려면 검사가 해당 로그를 읽지 않는다는 조건도 확보해야 한다.
- `volatile`: 외부 서비스·시간·난수·통제 불가 입력 등 현재성을 보장할 수 없으면 경계마다 새 검사를 요구한다. 해당 검사 직후에도 영구적인 정확성을 보장하는 증거는 아니다.

검사 전후 관측 입력이 달라지거나 필요한 writer 종료를 확인할 수 없으면 성공 증거를 확정하지 않는다. lease는 협업 기록이며 OS 차원의 쓰기 차단 증명이 아니다. 진정한 동시 스냅샷을 만들 수 없으면 해당 입력을 쓰는 작업이 없는 안전한 지점에서 검사한다. 전후 지문 비교만으로 중간에 바뀌었다 돌아오는 쓰기까지 검출한다고 주장하지 않는다.

```text
Reusable(g,t) = trusted passing record
  AND same obligation/role/revision/check/runtime
  AND complete, unchanged observation context
  AND no mandatory fresh observation at this boundary

Execute_t = FreshRequired_t ∪ {g required now : NOT Reusable(g,t)}
```

검사 결과는 검사기가 만든 실제 실행 기록에서만 생성한다. 작업자가 쓴 “통과” 문구나 해시 하나로 인증하지 않는다. 새 증거 맥락은 기존 STRUCTURE 저장 계층에 추가하는 방안을 사용하되, Gate 성공 기록과 함께 확인되어야 한다. PLAN은 그 결과를 반영하는 진행 상태다. 서로 불일치하면 완료로 승격하지 않는다. 이 증거 확장은 현재 구현에 없으며, 문서만 바꾸어 활성화할 수 없다.

계약 변경은 관련 증거를 무효화하고, 영향 범위를 증명할 수 없으면 해당 scope 전체를 무효화한다. 통합이 부품 내용을 고치면 관련 지역 검사를 다시 수행한다. 그룹 병합만으로 산출물이 바뀌지 않았다면 구조 검사만 갱신한다. 완료 주장 직전에 이 조건을 다시 확인한다.

수동 검토 기록도 검토 대상과 계약 버전에 묶인다. 과거에 검토했다는 표시만으로 변경된 산출물/요구사항을 통과시키지 않는다. 검토 범위를 좁혀 식별할 수 없으면 관련 전체 스냅샷이 바뀔 때 수동 증거도 무효화한다.

## 7. 반환 처리, 멱등성, 호스트 경계

제안하는 단일 진입점은 `advance`다. 이는 새 데몬이 아니라 기존 스킬에서 호출하는 사건 처리 명령이다. 실제 CLI/API 이름은 구현 단계에서 정한다.

```text
advance(observedEvent):
  실제 attempt/반환/필요한 writer 정지 사실 확인
  이전에 같은 event를 처리했는지 확인
  pending transaction이 있으면 먼저 복구
  현재 계약과 증거 상태 검사
  필요한 지역 공식 검사만 실행
  실패/수동 판단 필요이면 구조화된 후속 조치 반환
  성공 증거와 VERIFIED를 기록하고 정확한 lease 해제
  필요한 경우에만 그룹 재계산
  다음 배정을 계산해 간단한 결과 반환
```

이미 처리된 event라도 현재 증거가 낡았다면 과거 `launch` 명령을 재생하지 않는다. 사건 반영은 멱등적으로 하고, 출력은 현재 상태에서 재계산한다. 같은 event ID에 다른 내용은 오류다. 동일 반환은 동일 공식 검사를 중복 예약하지 않는다.

검사 도중 중단돼 실행 완료 기록이 없으면 통과로 추정하지 않는다. 새 정책의 자동 재시도 대상 검사는 읽기 전용이거나 격리된 임시 공간에서 반복 가능해야 한다. 부작용 있는 CHECK의 재실행 안전성을 모르면 검토가 필요하다. 이벤트 멱등성이 외부 프로세스·서비스 부작용의 exactly-once를 보장하지 않는다.

허용된 CHECK와 호출 스크립트에 대한 기존 검사·승인 경계는 유지한다. 자동 처리라는 이유로 새 명령을 자동 승인하지 않는다. 모델이 이해하는 규칙과 달리 실제 구현에서 호출 스크립트 변경 감지까지 필요하면 새 증거/검사기 식별에 포함해야 한다.

출력은 `continue`, `repair`, `review`, `wait`, `integrate`, `complete`와 원인 ID·대상 ID만 기본 제공하고, 상세 내용은 오류 조사 때 요청한다. 이 결과 중 `continue`는 원자적 실행 허가가 아니다. 호스트는 실행 직전 최신 소유권/상태를 확인하고 native agent 도구를 호출한다. 스킬 스크립트만으로 native agent 호출이 가능해진다고 가정하지 않는다. 읽기 전용 status/advice는 반복 호출해도 작업을 시작하지 않는다.

## 8. LLM이 개입하는 조건

부모 LLM의 의미 판단은 최초 계약, 계약에 지정된 수동 의무, 새로운 설계 문제, 최종 요청 대조에 집중한다. 정상 반환의 상태 정리·검사 결과 합산·배정 재계산은 스크립트가 수행한다.

단순 검사 실패는 해당 작업자에게 구조화된 실패 근거를 전달한다. 실패가 새 정보 없이 반복되거나 요구사항 해석/접근 경계 변경을 요구하면 부모 검토로 올린다. 부모에게 올리는 것이 성공이나 작업 포기를 의미하지 않는다. 하위 작업자의 구현·수정에는 계속 LLM 비용이 든다.

정상 성공 후 계산기 내부 소스를 매번 다시 읽지 않는다. 계산기 변경, 실패, 상태 불일치, 의미적 의심이 있을 때 조사한다. 참조 문서도 선택한 기능에 필요한 것만 읽는다. 실제 모델 호출 횟수는 호스트 제약과 다르므로 '중간 의미 재판단 감소'와 '모델 호출 0회'를 혼동하지 않는다.

## 9. 완료·Stop hook

```text
Done = current contract covered
  AND every required obligation has current accepted evidence
  AND actual integration obligations passed
  AND required manual outcomes reviewed
  AND no unresolved report/attempt/lease/journal
  AND no orphan/abandoned/deferred required work
  AND final request reconciliation passed
```

Stop hook은 계속 상태만 검사한다. 훅이 테스트를 실행하거나 모델을 직접 호출하지 않는다. root의 증거 감사 Gate는 위 조건을 확인하며 자기 자신을 검사하는 순환을 만들지 않는다. 최종 스냅샷 이후 외부 수정이나 새로운 작업 사건은 root 증거를 무효화해야 한다. 기존 훅만으로 외부 파일 수정의 즉시 감지를 보장하지 않는다.

무진전 탈출과 abandon 인계는 성공과 별개다. 검사 수를 줄이려고 미해결 작업을 완료로 표시하지 않는다.

## 10. 예상 효과와 한계

leaf 공식 검사 수가 `L`, 통합 검사 수가 `J`인 단순한 성공 경로를 생각한다. 각 검사가 자식 자체 실행·부모 실행·직접 branch의 재실행에서 중복됐다는 조건에서는 기존 해당 부분이 `3L+J`, 제안이 `L+J`가 된다. 감소량은 `2L`이다.

이것은 조건부 실행 횟수 예시다. 원본 전체가 항상 이 횟수라는 뜻이 아니며, 개발 중 테스트·실패 재시도·새 수동 의무·외부 상태 검사·증거 기록 비용을 제외한 값이다. 제안도 의존성을 완전히 모르면 보수적 재검사가 필요하다. LLM 토큰이나 경과 시간이 같은 비율로 감소한다고 주장하지 않는다.

예를 들어 부품 지역 검사 4개와 통합 검사 1개라면 해당 중복 경로의 13회가 5회로 줄 수 있다. 조립 중 부품이 바뀌면 해당 검사는 다시 필요하다. 오류를 더 늦게 발견해 수정비가 늘 가능성도 있으므로 품질·재작업 비용을 함께 측정해야 한다.

## 11. 구현 시 변경 대상과 단계

이 목록은 후속 구현 계획이며 이번 설계 작업에서 적용하지 않는다.

1. 증거 맥락·무효화·멱등적 반환 처리의 저장 형식과 검사기를 추가한다. 기존 검사 승인과 실행기 기능은 재사용한다.
2. 구조 검사기와 scheduler가 현재 공식 증거를 확인하도록 연결한다. Gate 기록과 receipt 불일치는 차단한다. 미통과 상태에서 의존 작업을 시작하지 못하게 한다.
3. `SKILL.md`, `references/orchestration.md`, `references/gates.md`, `references/structure.md`, `references/handoff.md`, `references/token-economy.md`, `templates/gates-leaf.md`, `templates/gates-node.md`를 함께 바꾼다. N1의 재귀 실행과 새 증거 감사 정책을 동시에 활성화하지 않는다.
4. 기존 scope는 기존 방식으로 유지한다. 새 scope에서 새 정책을 명시적으로 선택하고, 진행 중 scope를 전환하려면 의무·활성 작업·증거의 대응을 검토한다. 첫 실행에서 과거 기록을 새 증거로 무조건 인정하지 않는다.
5. 고정 과제와 숨겨진 기능·오류 검사, 변경 요청, 중단/복구 시나리오로 원본·현재본·새 정책을 비교한다. 통과율뿐 아니라 결함·재작업 비용도 측정한다.

## 12. 검증 기준

- 정상 무변경 반환에서는 같은 의무의 공식 성공 검사를 중복 실행하지 않는다.
- 실제 부모 독립 검사는 생략되지 않으며, 작업자의 보고로 대체되지 않는다.
- 중복 이벤트와 저장 후 재시작은 새 작업/검사를 중복 생성하지 않는다.
- 산출물·검사·도구·계약·관련 환경 변화가 낡은 증거로 통과하지 못한다.
- 의존성 불명/외부 상태/동시 쓰기는 무조건 재사용으로 처리하지 않는다.
- 반환 실패·수동 의무·인계·고아·lease·복구 대기 상태가 있으면 완료하지 않는다.
- 통합 후 변경은 지역/통합 증거를 적절히 무효화한다.
- 모든 공식 체크를 삭제해서 절감을 만드는 방식은 비교에서 탈락한다.

모델 검산은 이 정책의 작은 사례에 대한 검토다. 실제 런타임 구현, 품질 동등성, 전체 비용 감소는 후속 구현과 실험으로 확인해야 한다.

실행 기록: `work/minimal-verification/design-check.mjs`로 28개 시나리오와 독립 작업 반환 순서 24가지를 확인했다. 정상 모델은 지역 공식 검사 4회와 통합 검사 1회로 종료했고, 관련 부품 변경 뒤에는 해당 지역 검사와 통합 검사만 더해 총 7회가 됐다. 변경 없는 중복 보고·재시작은 횟수를 늘리지 않았다. 산출물/계약 변경 뒤 수동 검토 증거 재사용도 차단했다. 구체적 결과는 사용자 산출물 `minimal-verification-design-checks.json`에 기록한다. 상태 플래그·입력 완전성·신뢰된 부모 기록을 가정한 작은 모델이므로 실제 고아 탐지 구현이나 저장 내구성까지 검증한 것으로 해석하지 않는다.
