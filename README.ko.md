# Kill_bezzangyi

[English](README.md) · 한국어

AI 에이전트에 일을 맡기면 요구사항 일부를 빠뜨리거나, 검증을 건너뛰거나, 아직 할 일이 남았는데도 끝났다고 답하는 경우가 있습니다. [unlazy](https://github.com/Leonxlnx/unlazy)는 이런 문제를 줄이기 위한 스킬입니다. 작업 전에 확인 가능한 완료 조건을 정하고, 큰 작업은 필요에 따라 나누고, 결과를 검사한 뒤 완료를 보고하도록 합니다. 끝내지 못한 일도 숨기지 않고 남겨, 무엇이 아직 해결되지 않았는지 알 수 있게 합니다.

Kill_bezzangyi는 이 완수 원칙을 이어받았습니다. 작업을 끝까지 수행하는 과정에서 같은 판단과 검증을 되풀이하는 비용을 줄이는 것이 목표입니다.

작업을 나누고 의존 관계까지 정했다면, 그다음에는 규칙대로 처리할 수 있는 일이 많습니다. 지금 시작할 수 있는 작업은 무엇인지, 어떤 작업을 동시에 진행해도 되는지, 앞서 통과한 검증이 아직 유효한지 같은 것들입니다. Kill_bezzangyi는 이 부분을 스크립트에 맡겨, 작업을 넘길 때마다 모델이 같은 내용을 다시 읽고 판단하는 일을 줄입니다.

작업의 의미를 해석하고, 코드를 작성하고, 결과의 적절성을 판단하는 역할은 에이전트가 맡습니다. 스크립트는 명시된 규칙에 따라 다음 작업을 계산하고 기록된 상태를 확인합니다.

![Kill_bezzangyi의 작업 흐름: 작업 정의, 배정 계산, 호스트를 통한 에이전트 실행, 결과 검증, 통합. 다음 작업은 배정으로 돌아가고, 추가 분할은 부모 검토를 거칩니다.](docs/assets/architecture.png)

*스크립트가 계산한 배정안을 바탕으로 호스트가 에이전트를 실행합니다. 선언된 입력이 바뀌지 않았다면 유효한 검증 기록을 재사용합니다. 순차 작업은 한 에이전트가 이어서 수행할 수 있으며, 그림 속 작업대 수가 필요한 에이전트 수를 뜻하지는 않습니다.*

## 시작하기

저장소 전체를 내려받습니다. `SKILL.md`와 함께 들어 있는 스크립트, 참조 문서, 템플릿이 필요합니다.

```sh
git clone https://github.com/EESIZ/kill_bezzangyi.git
cd kill_bezzangyi
```

로컬 파일을 읽고 명령을 실행할 수 있는 에이전트에 `SKILL.md` 경로와 작업을 전달합니다.

```text
<저장소 경로>/SKILL.md를 읽고 이 작업에 적용해줘:
<원하는 결과와 지켜야 할 조건>
```

스킬 설치를 지원하는 에이전트라면 해당 도구의 방식에 맞춰 이 디렉터리를 등록해도 됩니다. 스킬 이름은 `kill-bezzangyi`입니다.

에이전트는 먼저 `GATES.md`에 확인 가능한 완료 조건을 적습니다. 작은 작업은 한 에이전트가 처리합니다. 독립적으로 진행할 부분이 있으면 작업을 나눌 수 있고, 부모 에이전트가 각 결과를 받아 검사한 뒤 합쳐진 결과도 확인합니다.

### 의존성 및 실행 환경

- Node.js 16 이상: 스크립트, 테스트, 선택적 Stop 훅 실행에 필요합니다.
- 외부 런타임 패키지 의존성은 없습니다. Node.js 표준 라이브러리를 사용합니다.
- `SKILL.md`를 읽을 수 있는 에이전트가 필요합니다. 병렬 작업에는 실행 도구의 서브에이전트 지원도 필요합니다.
- 개별 `CHECK` 명령에 필요한 도구는 `PATH`에 있어야 합니다.
- Stop 훅은 Claude Code용 선택 기능입니다. 저장소를 내려받는 것만으로 설치되지는 않습니다.

## unlazy에서 달라진 부분

| 구분 | Kill_bezzangyi의 처리 방식 |
|---|---|
| 다음 작업 배정 | 선언된 의존 관계, 읽기·쓰기 범위, 공유 자원, 진행 중인 작업의 점유 상태, 남은 실행 자리를 계산해 시작·대기·검토할 작업을 알려줍니다. |
| 작업 분할과 재편성 | 같은 요청을 재시도해도 중복 반영되지 않도록 변경을 기록합니다. 중단된 변경을 복구하고, 작업의 완료 조건과 부모의 통합 검사가 빠지지 않았는지 확인합니다. |
| 진행 중 발견한 추가 분할 | 작업자가 부모에게 보고합니다. 부모가 작업 중지를 확인하고 인계 내용을 검토한 뒤, 다음 논리 턴에서 다시 배정할 수 있습니다. |
| 완료 판정용 검사 | 부모 에이전트가 맡습니다. 작업자는 개발에 필요한 테스트를 수행하되, 완료 판정용 검사 전체를 먼저 반복할 의무는 없습니다. |
| 재검증 | 선언된 입력과 검증 조건이 그대로라면 기존 통과 기록을 재사용합니다. 실제로 결과를 합치는 지점의 통합 검사는 유지합니다. |

예를 들어 독립적인 두 기능이 각각 검사를 통과했다면, 부모는 그 기록이 아직 유효한지 확인하고 두 기능이 함께 동작하는지 검사합니다. 결과를 부모에게 넘겼다는 이유만으로 각 기능의 검사를 전부 다시 실행할 필요는 없습니다. 관련 입력이 바뀌었다면 다시 검사해야 합니다.

기존 Gate 실행기, 명령 승인 방식, 상태를 읽는 Stop 훅은 유지합니다. 새 검증 방식에서는 검사를 실행할 시점과 기존 결과를 재사용할 조건을 바꿨습니다.

## 사용한 수식과 연구 근거

아래 수식은 실제 구현이 무엇을 계산하는지 설명합니다. 널리 알려진 알고리즘을 적용한 부분도 있고, 이 프로젝트의 작업 규칙을 수식으로 표현한 부분도 있습니다. 인용한 논문이 이 스킬의 토큰 절감 효과를 입증한 것은 아닙니다.

작업 그래프를 $G=(V,E)$라 하고, $u\to v$는 작업 $v$가 $u$의 결과를 필요로 한다는 뜻입니다. $u\leadsto v$는 여러 작업을 거쳐서라도 그런 의존 관계가 이어진다는 뜻입니다.

### 1. 두 작업을 동시에 진행해도 되는가?

작업 $i$가 읽는 대상을 $R_i$, 쓰는 대상을 $W_i$로 둡니다. 파일뿐 아니라 별도로 식별한 공유 자원에도 같은 조건을 적용합니다.

$$
B(i,j) \iff
W_i\cap W_j=\varnothing
\;\land\; W_i\cap R_j=\varnothing
\;\land\; R_i\cap W_j=\varnothing
$$

$$
\mathrm{Independent}(i,j)
\iff B(i,j)\land\neg(i\leadsto j)\land\neg(j\leadsto i)
$$

같은 자료를 함께 읽는 것은 괜찮습니다. 하지만 같은 대상을 수정하거나, 한쪽이 수정 중인 대상을 다른 쪽이 읽는다면 독립 작업으로 배정하지 않습니다. 서로의 결과에 의존하는 경우도 제외합니다.

**근거:** A. J. Bernstein, *Analysis of Programs for Parallel Processing* (1966), [DOI](https://doi.org/10.1109/PGEC.1966.264565). [HPF 공식 명세](https://hpff.rice.edu/versions/hpf2/hpf-v20/node68.html)에도 이 조건이 설명돼 있습니다. 여기에 의존 경로 확인과 보수적인 파일 패턴 비교를 더해 작업 배정에 적용했습니다. 읽기·쓰기 대상은 빠짐없이 선언해야 합니다. **구현:** [conflicts / schedule](scripts/lib/schedule.mjs).

### 2. 지금 어떤 작업을 시작할 수 있는가?

$D_t$는 검증을 마친 작업, $U_t$는 아직 끝나지 않았고 현재 실행 중도 아닌 작업, $L_t$는 작업 영역의 점유권을 아직 놓지 않은 작업입니다.

$$
Q_t=\{v\in U_t:\mathrm{Pred}(v)\subseteq D_t
\land \mathrm{Pred}(v)\cap L_t=\varnothing\}
$$

즉, 선행 작업의 검증과 점유권 해제가 모두 끝나야 다음 작업의 후보가 됩니다. 스크립트는 작업 ID 순서로 후보를 살펴보고, 실행 중인 작업 및 이미 고른 후보와 충돌하지 않는 작업을 남은 자리만큼 선택합니다.

$$
|S_t|\leq\max(0,k-|A_t|)
$$

$S_t$는 새로 배정할 작업, $A_t$는 실행 중인 작업, $k$는 동시 실행 한도입니다. 상태 기록에 모순이 있으면 배정 대신 검토를 요청합니다.

**근거:** A. B. Kahn, *Topological sorting of large networks* (1962), [DOI](https://doi.org/10.1145/368996.369025). 코드에서는 Kahn의 위상 정렬로 순환 의존성을 검사합니다. 준비 상태·점유권·후보 선택 규칙은 프로젝트에서 추가한 것이며, Kahn의 논문에서 가져온 배정 정책은 아닙니다. 전체 비용이 가장 작은 조합을 찾는 최적화도 하지 않습니다. **구현:** [parsePlan / schedule](scripts/lib/schedule.mjs).

### 3. 나눈 작업은 언제 다시 묶을 수 있는가?

$\mathcal P$는 작업을 나눈 그룹들의 집합입니다. 각 그룹을 하나의 점으로 본 그래프 $G/\mathcal P$에도 순환이 없어야 합니다. 합칠 그룹 $M$ 안에서 아직 끝나지 않은 작업끼리는 선후관계가 있어야 합니다.

$$
\mathrm{DAG}(G/\mathcal P')
\quad\land\quad
\forall u\ne v\in M_{\mathrm{unfinished}},
\;(u\leadsto v)\lor(v\leadsto u)
$$

이렇게 해야 그룹을 합친 뒤 서로를 기다리는 순환이 생기지 않고, 독립적으로 진행할 수 있는 미완료 작업을 한 그룹에 묶어 버리지 않습니다. 실행 중이거나 점유권이 남은 작업도 재편성하지 않습니다. 그룹을 합쳐도 작업 자체나 완료 조건은 지우지 않습니다.

**참고한 원리:** Herrmann 외, *Acyclic partitioning of large directed acyclic graphs*, Inria RR-9163 (2018), [저자 소속 대학 공개본](https://research.sabanciuniv.edu/35222/1/RR-9163.pdf). 그룹 사이에도 비순환성을 유지해야 한다는 개념을 참고했습니다. 논문의 다단계 분할 알고리즘을 그대로 구현하거나 성능 수치를 가져온 것은 아닙니다. 위의 미완료 작업 조건은 프로젝트 자체 규칙입니다. **구현:** [calculateStructure](scripts/lib/structure.mjs), [별도 구조 검산](scripts/lib/structure-check.mjs).

### 4. 여기서 말하는 복잡도는 무엇인가?

구조 계산기는 세 가지 값을 반환합니다.

$$
C=(|\mathcal P|,\ |E_{\mathcal P}|,\ d_{\max})
$$

순서대로 그룹 수, 그룹 사이의 서로 다른 방향 연결 수, 기록된 최대 분할 깊이입니다. 깊이는 다음처럼 계산합니다.

$$
d(v)=
\begin{cases}
0 & \text{if no split is recorded for }v\\
1+\max_{c\in\mathrm{children}(v)}d(c) & \text{otherwise}
\end{cases}
$$

분할하지 않은 작업의 깊이는 0이고, 분할했다면 가장 깊은 자식에 1을 더합니다.

**프로젝트에서 정한 지표입니다.** 선언된 작업 구조를 보여주는 값이며, 토큰 사용량·실패 확률·아직 발견하지 못한 하위 작업 수를 예측하지 않습니다. 논문에서 검증된 LLM 복잡도 공식도 아니며, 이 값만으로 분할 깊이를 자동 결정하지도 않습니다. **구현:** [calculateStructure의 complexity 반환값](scripts/lib/structure.mjs).

### 5. 작업 누락과 중복 반영은 어떻게 확인하는가?

부모 작업을 남겨 둔 채 새 자식 $C_{\mathrm{new}}$를 추가하면 다음 관계를 확인합니다.

$$
V'=V\cup C_{\mathrm{new}},
\qquad
\biguplus_{P\in\mathcal P'}P=V'
$$

기존 작업은 보존하고 새 작업만 추가하며, 각 작업은 정확히 한 그룹에 속해야 한다는 뜻입니다. 기존 작업 ID, 의존 관계, Gate 정의도 유지됐는지 확인합니다. 최종 검사에서는 미완료 작업, 미처리 보고, 실행 중인 작업자, 남은 점유권도 확인합니다.

구조 변경 이벤트 $e$가 성공적으로 반영됐다면, 같은 변경 요청 ID와 같은 내용으로 재시도해도 저장된 상태가 다시 바뀌지 않아야 합니다.

$$
T_e(T_e(S))=T_e(S)
$$

이것이 멱등성입니다. 같은 ID로 다른 내용을 보내면 거절합니다. 새로운 구조 이벤트만 논리 턴을 늘리며 재시도는 늘리지 않습니다. 분할 보고는 보고한 턴보다 뒤에서, 반환·중지 확인·부모 검토·점유권 해제를 마친 뒤 수락할 수 있습니다.

**프로젝트 자체의 보존 조건과 멱등성 규칙입니다.** 특정 논문의 식을 그대로 가져온 것은 아닙니다. 기록의 일관성을 검사하는 것이므로, 에이전트가 처음부터 요구사항을 모두 기록했는지 또는 OS 프로세스가 실제로 멈췄는지까지 증명하지는 않습니다. **구현:** [verifyTransition](scripts/lib/structure-check.mjs), [applyStructure / 복구 처리](scripts/lib/structure-store.mjs), [인계 규칙](references/handoff.md).

### 6. 통과한 검사는 언제 재사용하는가?

검증 기록을 남긴 검사에 대해 다음 조건을 확인합니다.

$$
\mathrm{Reuse}
=\mathrm{Accepted}\land\mathrm{Closed}\land\mathrm{AllGatesMet}
\land(H_{\mathrm{context}}=H_{\mathrm{saved}})
\land(H_{\mathrm{ledger}}=H_{\mathrm{savedLedger}})
$$

앞서 검사를 통과했고, 입력 범위가 완전하다고 선언했으며, 모든 Gate가 충족된 상태여야 합니다. 현재 검증 조건과 검사 기록의 지문도 저장 당시와 같아야 합니다.

SHA-256 지문에는 선언한 입력의 내용, 검증 정책, Gate 정의, 해당 작업 계획의 개정 번호, 검사기 코드, 실행 환경이 포함됩니다. 검사 기록의 지문에는 증거도 포함됩니다. 호출자가 기대하는 정책을 별도로 전달했다면 그 정책 역시 일치해야 합니다.

**관련 연구:** Mokhov, Mitchell, Peyton Jones, *Build Systems à la Carte* (ICFP 2018), §4.2.2, [저자 공개본](https://simon.peytonjones.org/assets/pdfs/build-systems-original.pdf). 이 논문의 verifying trace는 기록한 해시를 이용해 결과가 여전히 유효한지 판별합니다. 여기서는 이 일반 원리를 완료 검사 기록에 맞춰 구성했으며, 논문의 빌드 시스템을 그대로 구현한 것은 아닙니다. 입력의 완전성·결정론성과 다른 작업자의 쓰기 중지는 명시적으로 확인해야 합니다. 해시가 같다는 사실만으로 이 전제까지 증명되지는 않습니다. **구현:** [context / inspectReceipt](scripts/lib/verification.mjs), [완료 검사 실행기](scripts/verify-once.mjs).

## 측정 결과

**A는 원본 unlazy**, **B는 초기 Kill_bezzangyi**, **C는 검증 절차를 줄인 현재 버전**입니다.

| B 대비 C의 변화 | 총 토큰 | 소요 시간 |
|---|---:|---:|
| 다음 작업을 배정하는 시험 | −45.1% | −31.2% |
| 구현부터 완료까지 수행하는 시험 | −0.25% | −3.0% |

개선이 가장 뚜렷했던 곳은 다음 작업을 판단하는 구간입니다. 원본 unlazy인 A와 비교해도 이 구간의 토큰은 43.4% 줄었습니다. 다만 **전체 작업의 토큰은 A보다 79.6% 많았습니다.** 해당 전체 작업 시험에서 A는 서브에이전트를 쓰지 않았고 B와 C는 일부 실행에서 사용했으므로, 실행 방식의 차이도 결과에 포함돼 있습니다.

각 버전은 전체 작업 16회와 배정 판단 16회에서 정해 둔 검사를 모두 통과했습니다. C는 실험 전 회귀 검사 282개도 통과했습니다. 이 결과만으로 품질이 같거나 언제나 비용이 적게 든다고 결론 내리지는 않습니다. 유형별 반복은 2회이며, C는 기존 A/B 시험 이후에 실행했습니다. 토큰을 실제 청구 금액으로 환산하지도 않았습니다.

자세한 내용은 [전체 비교 보고서](research/comparison-ABC-results-20260923.md)와 [측정 방법](research/comparison-protocol.md)에 있습니다.

## 적용 범위

스크립트는 에이전트가 선언한 정보를 바탕으로 계산합니다. 숨은 의존 관계를 모두 찾아내거나, 작업 분해 자체가 올바르다고 증명하거나, 병렬 실행이 더 저렴하다고 보장하지는 않습니다.

검증 결과를 재사용하려면 결과에 영향을 주는 입력을 빠짐없이 선언해야 합니다. 같은 입력에서 검사 결과가 일정해야 하고, 검사 중에 다른 작업자가 그 입력을 바꾸고 있어서도 안 됩니다. 이 조건은 스크립트가 알아서 알아내는 것이 아니라 명시적으로 확인하고 선언하는 사항입니다. 확인할 수 없으면 새로 검사합니다. 사람이 판단해야 하는 항목과 통합 검사도 남아 있습니다.

에이전트의 실제 실행과 중지는 호스트 도구가 담당합니다. 모든 실행을 자동으로 이어 가는 제어기는 아직 구현하지 않았습니다. Stop 훅은 기록된 상태를 확인하며, 파일 변경을 실시간으로 감시하지 않습니다.
