# 재귀 분할·병합의 결정론적 규칙안

상태: 설계 제안. 현재 schedule.mjs에 재귀적인 실행 중 분할이나 동적 병합이 구현됐다는 뜻이 아니다. 기존 Gate·검증·Stop hook 의미는 유지한다.

## 1. 두 종류의 구조를 분리한다

- 논리 작업 그래프 G=(V,E): 실제로 해야 할 일과 선후관계. 원래 작업 ID, 요구사항, Gate, 증거의 출처를 보존한다.
- 실행 묶음 P: 현재 어떤 작업들을 한 에이전트에 맡길지 나타내는 분할(partition). 병합은 이 묶음을 바꾼다.

묶음을 합쳐도 원래 작업·Gate를 삭제하지 않는다. 중간 작업의 검증 결과는 외부 후속 작업에 즉시 제공하며, 묶음 전체가 끝날 때까지 기다리는 새로운 장벽을 만들지 않는다.

결과의 합류(join)는 관련 결과를 모으고 통합 Gate를 검사하는 행위다. 실행 단위 병합(coarsening)은 여러 작업을 같은 담당 단위로 묶는 행위다. 두 행위를 구별한다.

## 2. 입력 계약

LLM이 각 작업의 유한한 분할 후보 구조, 요구사항 대응, 읽기/쓰기 집합, 선후관계, 완료 Gate를 명시한다. 스크립트는 명시된 구조를 검증하고 계산한다.

없음과 모름을 구분한다.
- 분할 후보를 검토했고 병렬 부분이 없음: 현재 선언 아래 단일 실행 단위.
- 분할 후보 또는 접근 정보가 없음/불완전함: UNKNOWN. 분해 불가능 판정이나 완료 근거로 사용하지 않는다.

실행 상태·소유권·계획 버전·완료 이벤트 ID도 입력이다. 동일한 정규화된 입력과 정책 버전에 대해서 같은 결과를 반환한다. 미래 작업의 의미·입출력을 스크립트가 스스로 발견하지 않는다.

## 3. 독립성 규칙

R_i는 읽는 대상, W_i는 변경하는 대상, i→*j는 직접 또는 간접 선행관계다.

I(i,j) =
  not(i→*j) and not(j→*i)
  and W_i∩R_j=∅
  and W_j∩R_i=∅
  and W_i∩W_j=∅

파일뿐 아니라 공유 DB·포트 등도 동일한 자원 모델에 포함한다. 해당 모델에서 충돌 없음이 확인된 경우만 독립으로 인정한다. 애매한 겹침은 독립으로 인정하지 않는다.

이는 Bernstein 조건과 작업 선후관계를 결합한 프로젝트 판정이다. 조건 미충족은 병렬화 불가의 일반적인 수학적 증명이 아니라, 이번 정책 아래 독립 실행을 인정하지 않는다는 뜻이다.

## 4. 분할 규칙

작업 T의 후보 내부 그래프 H_T에서 독립적인 두 미완료 작업이 존재하면 병렬 구조가 있는 것으로 판정한다.

Parallel(H_T) = exists a≠b in unfinished(H_T): I(a,b)

Split(T) =
  CompleteDeclaration(H_T)
  and ContractPreserved(T,H_T)
  and Acyclic(G after expansion)
  and Parallel(H_T)
  and EligibleBoundary(T)
  and NotExpanded(T, revision)

ContractPreserved:
- 부모의 모든 필수 결과가 자식 또는 부모 통합 Gate에 대응된다.
- 외부에서 기다리던 부모 결과는 부모 통합 검증 후에만 공개된다.
- 자식의 선행 작업은 실제 외부 입력 또는 다른 자식이다. 자식이 부모 최종 완료를 기다리게 만들어서는 안 된다.
- 아직 남은 부모 자체의 일도 명시적인 자식/통합 작업으로 남긴다.
- 체크된 부모의 과거 증거를 새로운 자식에게 자동 복제하지 않는다.

순차 전처리 뒤에 병렬 가지가 있는 후보도 분할 대상이다. 현재 당장 둘을 실행할 수 있다는 뜻은 아니며, READY 조건이 나중에 실행 시점을 결정한다.

EligibleBoundary:
- 실행 전에 확정된 구조이거나, 기존 규칙에 맞게 검증·기록·소유권 정리가 끝난 정지 경계다.
- 실행 중인 작성자, 부분 변경, 처리 중인 도구 호출이 있는 동안 구조를 바꾸지 않는다.
- 현재 unlazy의 미검증 leaf가 lease를 보유한 상황에서 임의로 해제·대체하는 작업은 이 설계로 허가되지 않는다. 그런 live leaf 전환은 별도 인계 프로토콜을 설계하기 전까지 검토 대상으로 남긴다.

## 5. 재분할 깊이

깊이는 처음/두 번째 분할에만 특별한 의미를 주지 않고 동일하게 계산한다.

D(T)=0                         현재 후보가 단일 실행 단위인 경우
D(T)=1+max D(child)             분할된 경우

이 값은 현재 명시된 분해 구조의 깊이다. 분할 후보가 미확정이면 확정 깊이라고 보고하지 않는다. 분해 깊이는 의존 그래프의 최장 경로 길이와 별도 값이다. 새 분할 후보가 추가되면 갱신한다.

재분할 여부는 깊이 점수 임계값이 아니라 독립성 규칙으로 결정한다. 깊이는 구조 설명·검사·진행 추적용이다.

## 6. 보수적인 병합 규칙

P의 두 실행 묶음 A,B를 병합할 후보로 본다. U는 A∪B에 속한 미완료 논리 작업들이다.

Chain(U) =
  for all distinct u,v in U:
    u→*v or v→*u

U에 작업이 0개 또는 1개면 Chain은 참이다.

Merge(A,B) =
  Quiescent(A,B)
  and ContractAndEvidencePreserved(A,B)
  and Acyclic(quotient graph after merge)
  and Chain(U)

의미:
- 작업 인계가 가능한 정지 경계에서만 묶는다.
- 남은 일들이 순차적으로 이어지거나, 한쪽/양쪽이 이미 검증 완료되어 병렬 이점이 사라진 경우를 대상으로 한다.
- 원래 부모가 같은지 여부는 필수 조건이 아니다. 다른 가지끼리도 위 조건을 만족하면 후보가 될 수 있다.
- 아직 서로 독립적인 일이 남아 있는 두 묶음은 합치지 않는다. 분할 규칙과의 즉각적인 왕복을 방지한다.
- 단순히 둘이 읽기/쓰기 충돌한다는 이유만으로 순서를 새로 발명하지 않는다. 필요하면 LLM이 선후관계를 보완한다.
- DAG인 원본을 임의로 묶으면 묶음 간 순환이 생길 수 있으므로 병합 후 그래프의 비순환성을 별도로 검사한다.
- 묶음 ID는 원래 작업 ID 목록을 정렬한 내용으로부터 안정적으로 만든다. 과거 작업 ID와 증거는 별도로 보존한다.

완료된 가지는 필수 부모 재검증과 통합 검증을 충족한 뒤 관리 화면에서 하나의 증거 묶음으로 접을 수 있다. 내부 증거를 실제로 삭제하거나 검증 명령의 입력에서 숨기지 않는다. 완료 접기 자체가 새 작업의 완료 증명은 아니다.

이 규칙은 최대한 많은 병합을 찾아내는 최적 알고리즘이 아니라, 병렬성을 의도적으로 보존하는 보수적인 초기 정책이다.

## 7. 관리 복잡도 측정

가중치 합산 점수 대신 서로 다른 값을 분리한다.

C_t=(Q_t, B_t, D_t)

- Q_t: 현재 관리하는 실행 묶음 수.
- B_t: 현재 묶음 경계를 넘는 의존 연결 수. 같은 묶음 쌍의 중복 연결은 한 개로 센다.
- D_t: 현재 명시된 재분할 트리의 최대 깊이.

두 묶음의 병합은 Q를 정확히 1 줄인다. 내부화된 연결은 B에서 빠진다. 원래 분해 이력의 깊이 D와 실제 남은 작업량이 반드시 줄어드는 것은 아니다.

Q 감소만을 목적으로 모든 작업을 한 덩어리로 만들지 않는다. 병렬성·선후관계·Gate 보존 규칙이 먼저다. 실제 토큰 비용과 시간 절감은 이 구조 값만으로 확정할 수 없다.

## 8. 반복 순서와 고정점

새 완료/검증 이벤트, 정식 계획 변경, 재개 시에만 계산한다.

1. 입력 버전, 이벤트 중복, 실행 기록·lease·Gate 일관성을 확인한다.
2. 검증 완료 상태를 반영한다. 단순 반환은 완료로 바꾸지 않는다.
3. eligible한 분할 후보를 안정적인 작업 ID 순서로 확장한다.
4. 병합 후보 쌍을 안정적인 ID 순서로 검사하고 하나씩 적용한 뒤 다시 계산한다.
5. 더 적용할 분할·병합이 없는 고정점에서 기존 READY/독립성/슬롯 규칙으로 실행 후보를 선택한다.
6. LLM이 기존 native 도구와 unlazy 검증 절차를 수행한다. 결과 이벤트가 오면 1로 돌아간다.

동률은 항상 정규화된 ID 순서로 해결한다. 완료 이벤트는 고유 키로 한 번만 반영한다. 동일 입력에서는 동일 권고를 반환하고, 실행 기록이 바뀌지 않은 채 재호출됐다는 이유로 새 에이전트를 생성하지 않는다. 입력 snapshot과 실제 claim/실행 사이의 변화는 기존 소유권 경계에서 다시 검사한다.

분할 이력은 원래 논리 작업 ID와 계획 버전에 붙인다. 병합된 실행 묶음을 새로운 미분석 과제로 취급해서 이미 확장한 같은 작업을 다시 분할하지 않는다.

고정된 유한 후보 구조에서는:
- 각 논리 작업 후보의 확장은 최대 한 번이다.
- 분할이 끝난 후 매 병합은 묶음 수를 하나 줄인다.
따라서 구조 변환만으로 무한 반복하지 않는다. 외부에서 무한히 새 계획을 추가하는 경우나 작업 자체가 끝나지 않는 경우까지 종료를 보장하는 것은 아니다.

현재 구현됨:

이 문서는 구현 승인 전 검토 가능한 규칙안이다. 기존 실행 기록과 lease를 가진 leaf를 자식 그래프로 전환하는 세부 저장 형식·인계 절차는 아직 구현하지 않았다. 기존 Gate·Stop hook 코드를 변경하지 않았으며 종료 보장·검증 강도를 약화하지 않는다.

## 10. 필수 구조 무결성 Gate

다음 Gate 규칙은 Task 3에서 `structure-check.mjs`의 구조 검사 및 `--final` 검사와 root S_STRUCTURE Gate로 연결했다. 실제 검산 전에는 통과했다고 기록하지 않는다.

| Gate | 충족 조건 |
|---|---|
| S1 작업 보존 | 분할·병합 이력에 있는 유효한 작업과 현재 연결된 작업이 대응된다. 제거·대체에는 명시적인 근거와 대응 관계가 있고 고아 작업이 없다. |
| S2 배정 일관성 | 실행 대상 leaf는 정확히 하나의 실행 묶음에 속한다. 실제 시작 기록·에이전트 식별자·소유권이 계획과 모순되지 않는다. |
| S3 통합 완료 | 필요한 자식 검증 및 부모 통합 Gate가 모두 충족된다. 단순 반환이나 묶음 병합을 완료 증거로 쓰지 않는다. |
| S4 종료 정리 | 최종 종료 시 실행 중 작업, 처리 중인 분할·병합, 미해결 abandon, 남은 scope 소유권이 없다. |

S1·S2는 분할·병합·재개 시 검사한다. S3는 해당 부모를 완료 처리하기 전에, S4는 최종 scope 정리 후 검사한다. 최종 root 검증은 이 조건들을 모두 재확인한다. 작업 중 실행자가 있다는 이유만으로 S4 미충족을 오류나 복구 루프로 처리하지 않는다.

기존 Stop hook은 이 Gate들의 기록된 미충족 상태를 읽어 성공처럼 종료되는 일을 막는 최종 장치로 활용한다. 기존 hook의 abandon 인계와 무진전 중단 장치는 성공 판정과 구분해서 유지한다.

### 오래된 PASS를 재사용하지 않는 규칙

- 구조 변경을 적용하기 전에 관련 구조 Gate를 미충족으로 표시한다.
- 변경 작업의 시작/완료 및 적용한 snapshot을 기록한다. 중간에 중단되면 미충족 상태가 남아야 한다.
- 구조·상태·실행 기록·소유권의 해당 snapshot을 실제 검사한 결과만 현재 증거로 인정한다.
- 검사 중 입력이 바뀌면 통과를 기록하지 않는다. 최종 보고 직전에 기존 --reverify 절차로 재검사한다.
- 현재 gate-check의 정의 digest는 CHECK/EXPECT/CWD를 묶지만 임의 외부 입력 파일의 변경을 자동 추적하지 않는다. Task 3은 관리된 변경 전 무효화와 검사 종료 시 snapshot 재확인을 추가했다. 외부 변경 후에는 여전히 명시적인 재검증이 필요하다.
- Stop hook에 기존 PASS가 보인다는 사실만으로 모든 입력이 최신이라고 간주하지 않는다.

변경 시 Gate 무효화, 작업 이력 보존, 실제 실행 기록과의 대조, 현재 snapshot에 대한 검사 결과 기록이 함께 구현돼야 한다. 선언적인 Gate 이름만 추가하면 고아 작업 탐지 기능이 생기는 것은 아니다.

검증할 사례: 분할 도중 중단, 에이전트 시작 후 handle 기록 실패, 자식 누락, 중복 배정, 미해결 abandon, 자식 반환 후 통합 누락, 남은 lease, 구조 변경 후 낡은 PASS, 무진전 인계.
