## 합의된 방향

- unlazy는 완수 규율에 유용하지만 토큰 비용이 문제다.
- 기존 1~6단계 흐름을 유지하고, 각 단계의 판단 기준을 명확히 하는 방향을 검토한다.
- 순차 구간은 한 에이전트가 담당하고, 독립적인 가지에서 서브에이전트로 분기하는 정책을 채택했다.
- 선후 의존관계와 Bernstein 읽기/쓰기 조건으로 독립성을 보수적으로 계산한다. 확률·임의 점수·비용 추정 임계값은 사용하지 않는다.
- 기존 스킬의 판단 시점에 계산 도구를 호출한다. LLM은 native 실행 도구와 의미 검토를 담당하며, 별도 실행 하네스를 만들지 않는다.
- 기존 PLAN·Gate·dispatch·lease가 권위 있는 상태다. ACCESS.json은 부족한 읽기 대상과 공유 자원만 보완한다.
- gate-check·dispatch-check·Stop hook 구현과 기존 전역 설치본은 유지한다. schedule.mjs, 멱등 구조 변경기 structure.mjs, 독립 검산기 structure-check.mjs를 기존 판단 시점에 연결한다.

## 출발점

`EESIZ/kill_bezzangyi`는 초기 확인 시 unlazy 원본 커밋 `16671491f6679ad9378f52604d3bc2415b4120c7`와 동일했다. 이 커밋의 이력을 유지해 파생 프로젝트로 시작했다. 브랜드 및 스킬 호출명만 변경하고 검사기 구현은 유지한다.

## 지금까지의 조사

- 설치본에도 토큰 절약 지침은 이미 있었다. 최신판 교체만으로 큰 절감을 보장할 수 없다.
- 원본에는 과업 복잡도를 계산해 Solo/분업을 선택하는 정량 분류기가 없다.
- PR #33은 동일 검사 공유 기능이다. 별도 인공 예제에서 시간·출력 감소를 관찰했지만 전체 에이전트 토큰 절감은 측정하지 않았다. 이 저장소에는 도입하지 않았다.
- 문헌은 복잡도 측정(Wood·WDQ), 분석 깊이 중단(HTA), 의존관계(DSM), 계산 가치 근사(BMPS)를 구분해 참고할 가치가 있다. 상세 출처와 한계는 [조사 기록](research/task-complexity.md)에 있다.

## 현재 구현 범위와 다음 검증

Task 2와 Task 3의 계획/검증 보고를 참조한다. Task 3은 부모의 ID·Gate를 통합 작업으로 남기는 재귀 분할, 실행 묶음의 보수적 병합, 독립 검산, operation ID 기반 멱등 반영, journal 복구, root S_STRUCTURE Gate를 추가한다. 계산 결과는 snapshot 시점의 조언이며 실제 claim·검증을 대신하지 않는다. 기록된 입력 밖의 의존성은 자동 발견하지 못한다. 전체 토큰·지연 절감은 실사용 비교로 검증해야 하며 아직 수치가 없다.

Task 4는 실행 중 발견한 분할을 영속 보고하고, 정확한 native 반환/정지 확인/부모 검토/lease 해제 후 다음 논리 턴에 수락한다. 해당 실행 시도만 인계 완료로 구분하며 새 시도는 다시 active다. 부모 Gate와 체크포인트를 남기고 자식 재귀 분할 및 통합 부모의 추가 분할을 지원한다. 보고를 수락·거절할 때까지 최종 완료는 허용하지 않는다. 사용법과 수식은 references/handoff.md와 references/structure.md에 있다.

정지와 의미 검토는 호스트/부모가 근거를 제공하는 사실이다. 스크립트가 OS 정지를 증명하지 않는다. 강제 종료로 남은 기존 filelock은 확인 후 정리해야 복구할 수 있다. 기존 Stop hook의 6회 무진전 해제와 abandon 인계는 유지하며 성공으로 취급하지 않는다. 과거 task_3 보고의 실행 후 분할 미지원 한계는 Task 4의 명시적인 인계 절차로 확장되었다.
